# v4.0.0과 v5.2.1 연동·저장 안정성 검토

검토일: 2026-10-10. 저장소의 [보관된 v4.0.0 서버](../gas/legacy/TeacherSignV4.gs)와 [현재 v5.2.1 서버](../Code.gs), 현재 화면·테스트를 비교했습니다. 각 학교의 실제 /exec에 설치된 버전은 별도 확인해야 합니다.

**파일 연결 유지·학교별 격리·관리자 인증은 개선되었습니다. 저장 실패 시 자료 보존과 대용량·동시 접속 성능까지 전반적으로 개선됐다고 단정할 수는 없습니다.** 아래 재현은 가상 Drive에서 진행했으며 실제 학교 자료를 변경하지 않았습니다.

## 개선된 부분

| 항목 | v4.0.0 | v5.2.1 | 판단 |
| --- | --- | --- | --- |
| 자료 파일 선택 | 같은 이름의 첫 검색 결과 사용 | 스크립트 속성의 지정된 파일 ID 사용 | 동명이 파일 혼동 감소 |
| 같은 Google 계정의 여러 학교·시험 설치 | 같은 이름의 DB·서명 시트를 공유할 수 있음 | 프로젝트별 폴더·DB·서명 시트·계정 파일 분리 | 학교별 자료·로그인 분리 개선 |
| 기존 v4 자료 연결 | 이름 검색으로 읽음 | 담당자가 원본 확인 후 복사·검증·연결하는 최초 이전 필요 | 최초 이전은 수동, 이후 같은 v5 프로젝트의 업데이트는 연결 유지 |
| 관리자 접근 | 연결키 확인 | 관리자 계정·세션·CSRF·로그아웃·만료 검증 | 인증 개선 |
| 연수·서명 입력 검증 | 제한적인 필수값·이미지 형식 확인 | 연수 필드·명단·서명 형식·요청 크기 등 추가 검사 | 잘못된 요청 차단 개선 |
| 같은 쓰기 요청 재전송 | 처리 결과 기록 없음 | 같은 요청 ID·내용의 성공 결과를 제한 시간 동안 재사용 | 완료된 중복 요청 방지 추가, 부분 실패 복구는 별도 |

같은 이름의 다른 DB가 검색 결과 맨 앞에 오는 상황을 가상 Drive에서 재현했습니다. v4는 다른 DB를 선택했으며 v5는 지정된 원래 DB를 읽었습니다. 지정된 파일 ID를 직접 바꾸거나 파일을 삭제하면 v5도 연결되지 않습니다.

## 먼저 보완할 부분

### 1. 기존 서명 교체 중 저장 실패 — 우선순위 높음

[참여자 서명 저장](../Code.gs#L394)은 기존 JSON 서명을 제거하고 JSON을 저장한 뒤 시트에 서명을 씁니다. [시트 저장](../Code.gs#L744)은 기존 서명 행을 먼저 삭제한 뒤 새 행을 추가합니다. 이후 쓰기 실패를 되돌리는 처리가 없습니다. 잠금은 동시 처리 충돌을 줄이지만 실패한 여러 파일의 변경을 되돌리지는 않습니다.

가상 시트의 새 행 추가 단계에 실패를 주입한 결과:

| 기존 서명 위치 | v4.0.0 | v5.2.1 |
| --- | --- | --- |
| 별도 시트에 기존 서명 1개 | 오류 응답, 기존 서명 0개 | 오류 응답, 기존 서명 0개 |
| JSON에 기존 서명 1개 | 오류 응답, 기존 서명 0개 | 오류 응답, 기존 서명 0개 |

일반적인 첫 서명 성공 시험과 다른 조건입니다. 이미 서명한 참여자가 다시 서명할 때 새 저장이 실패하면 기존 서명이 빠질 수 있음을 확인했습니다. v5에서 새로 생긴 문제는 아니지만 아직 해결되지 않았습니다. JSON과 시트를 나누어 변경하는 연수 삭제·관리자 서명 작업도 실패 중간 상태를 검토해야 합니다.

보완 방향: 새 서명 저장과 검증이 끝날 때까지 기존 서명을 보존하고, 중간 실패·결과 기록 실패에도 안전하게 재처리할 수 있도록 쓰기 순서와 복구 기록을 설계합니다. 시트 실패·DB 실패·응답 유실·중복 요청을 포함한 검증이 필요합니다. 이번 검토에서는 운영 코드를 변경하지 않았습니다.

### 2. 대용량 조회와 동시 접속 — 개선 여부 미확인

두 버전 모두 연수 JSON 전체를 읽고, 서명 조회에서는 [별도 시트 전체의 10개 열](../Code.gs#L716)을 읽습니다. 참여자에게 이미지가 반환되지 않아도 서버는 이미지 열까지 읽은 뒤 결과를 줄입니다. v5에서는 [조회·인증을 포함한 요청을 같은 프로젝트 잠금 안에서 처리](../Code.gs#L954)하고 인증 파일도 저장합니다. v4에도 쓰기 잠금이 있었으므로 동시 저장 잠금 자체를 새 개선으로 평가하지 않았습니다.

가상 시트에 다른 연수의 서명 1,000행을 넣고 서명이 없는 연수 하나를 조회한 결과, 반환 서명은 0개지만 읽은 시트 셀은 헤더 10개와 데이터 10,000개, 총 **10,010개**였습니다. 이는 읽기 범위 검증이며 실제 Google 응답시간 측정이 아닙니다.

자료가 쌓이거나 같은 학교에서 한꺼번에 접속하면 대기가 늘어날 가능성이 있습니다. 파일 이름 검색 비용을 줄인 효과와 인증·전체 읽기 비용을 합쳐 실제로 빨라졌는지는 학교 규모에 맞춘 측정이 필요합니다. 보완 방향은 연수별 조회, 필요한 열만 읽기, 기록 분리·보관, 읽기 잠금 범위 축소입니다.

### 3. 학교 전체 요청 제한 — 배포 규모 확인 필요

현재 GAS는 참여자 조회·서명 요청을 학교 전체에서 1분 창당 300회로 제한하고, 성공한 쓰기 처리 기록은 5분간 최대 200개를 보관합니다. 관리자 쓰기도 이 기록 한도를 함께 사용합니다. 한도에 도달하면 일시적으로 거절합니다. 이는 안전장치이며 처리 속도나 지원 인원에 대한 성능 보장은 아닙니다.

실제 학교에서 접속·새로고침·서명이 만드는 요청 수를 포함해 검증해야 합니다. [Google Apps Script도 실행 시간·동시 실행·서비스 할당량을 제한하며 초과 시 예외로 실행이 중단됩니다](https://developers.google.com/apps-script/guides/services/quotas). [프로젝트 잠금의 범위는 Google 공식 설명](https://developers.google.com/apps-script/reference/lock/lock-service)과 대조했습니다.

## 수동 백업 검토

**현재 기능으로 가능합니다. 앱의 전체 백업·복원 버튼은 아직 없습니다.** [교사용 매뉴얼 14번](교사용매뉴얼.md)의 네 단계로 현재 연결된 TrainingApp_DB.json과 TrainingApp_Signatures를 같은 날짜의 Drive 사본으로 보관합니다. 동명이 파일이나 이전 전 원본 대신 **현재 파일 ID**를 확인합니다.

학교 설정·계정까지 보관하려면 TeacherSign_Auth.json, 코드와 스크립트 속성도 담당자 전용 위치에 보관합니다. PDF 등록부는 프로그램 복원 자료를 대신하지 않습니다. 수동 복원은 두 자료의 일관성과 이후 새 자료를 확인한 뒤 진행해야 하며, 계정·세션 파일을 그대로 덮어쓰는 자동 복원은 제공하지 않습니다. 이전 도구의 백업에는 이전 이후 새 자료가 포함되지 않습니다.

## 검증 범위와 결과

- 기존 자동 테스트 **47개 통과**, 타입 검사 통과.
- GAS iframe 화면 검사 **12개**, 공용 사이트 화면 검사 **15개** 통과. 가상 학교의 설치·로그인·연수 등록·Excel 명단·익명 모바일 QR 서명·새로고침 후 기록 유지·계정 변경·로그아웃·학교별 격리를 확인했습니다.
- 추가 가상 실험 **7조건**: 위 두 버전·두 저장 위치의 실패 4조건, 동명이 DB 선택 2조건, 전체 시트 읽기 1조건. 실패 위험은 실제 저장 함수에 주입한 오류로 재현했습니다.
- 실제 Google 서버의 동시 부하, 실패 발생률, 장기간 누적 자료의 응답시간은 측정하지 않았습니다. 가상 테스트를 실제 서비스 속도·무손실 보장으로 해석하지 않습니다.
- 이번 반영은 매뉴얼·검토 결과입니다. 프로그램 코드·학교 파일 연결·운영 배포는 변경하지 않았습니다.

여러 학교에 널리 배포하기 전 우선 보완할 사항은 **서명 교체의 실패 안전성 → 수동 백업·검증 복원 기능 → 연수별 조회와 동시 부하 검증**입니다. 별도 유료 저장 서비스 없이도 우선 쓰기 절차와 조회 범위를 개선할 수 있습니다.
